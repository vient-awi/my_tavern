# 发布与更新流程

> 用途：说明本分支（性斗学园「全员性转」改版）**怎么改、怎么发、酒馆怎么加载**。
> 与 [自动更新链路风险说明.md](自动更新链路风险说明.md)（讲两条自动更新链路为何被停用）、
> [性转改动对照规则.md](性转改动对照规则.md)（讲同步上游时哪些地方必须翻译）配套阅读。

---

## 一、核心约定：加载的是 `@main`，不是标签

酒馆里加载脚本走 **jsDelivr 的 `@main` 链接**：

```text
https://cdn.jsdelivr.net/gh/vient-awi/my_tavern@main/dist/性斗学园/性斗学园脚本/index.js
```

**为什么不用版本标签：**

- 本仓库 CI 生成的标签（`v0.0.1` 之类）是从 `package.json` 的 `version` 推出来的，
  而该字段当前**不存在**，所以标签号与本项目的 `SCRIPT_VERSION`（见
  [scriptUpdater.ts:3](性斗学园脚本/scriptUpdater.ts#L3)）**对不上**，没有使用价值。
- `v3.6.x` / `v3.7.x` 这一串标签**是上游 `vincentrong2005/Fatria` 的**，由 `git fetch upstream` 带入本地，
  仅用于**对比上游版本**，不代表本分支的发布。

**标签的唯一用途**：对比上游是否更新。

```bash
git fetch upstream --tags
git tag -l 'v3.*' | sort -V | tail -5     # 看上游出到哪一版了
```

**jsDelivr 缓存**：`@main` 的缓存比版本标签长。发新版后在
<https://www.jsdelivr.com/tools/purge> 提交上面的完整 URL 即可手动刷新，不必等。

## 二、日常开发循环（改 → 构建 → 酒馆试 → 再改）

```bash
pnpm build:dev     # 或 pnpm watch 持续构建
```

产物落在 `dist/性斗学园/性斗学园脚本/index.js`。把它加载进酒馆看效果，
不满意就回去改 `src/`，重复，直到满意为止。

> **`dist/` 已在 `.gitignore` 中**，本地怎么构建都不会弄脏 `git status`。
> 这是有意的：`dist/` 可由 `src/` 随时重建，不该进版本控制。

### 本地调试时的构建模式

| 命令 | 模式 | 特点 |
| --- | --- | --- |
| `pnpm build:dev` | development | `eval-source-map`，体积大但报错能定位到源码行 |
| `pnpm build` | production | Terser 压缩 + `source-map`，**发版用这个** |

**两种模式的产物不可互相比较**，排查问题时注意当前用的是哪个。

## 三、发布：把稳定版 dist 推上去

确认某个版本稳定后：

```bash
pnpm build                                       # 1. 生产模式构建
git add -f dist/性斗学园/性斗学园脚本/index.js     # 2. 强制加入（-f 绕过 .gitignore）
git commit -m "发布脚本产物 <说明>"
git push
```

### 关于 `-f`（这是本流程唯一的特殊动作）

`dist/` 在 `.gitignore` 里，普通 `git add` 加不进去，必须用 `-f` 强制。
**只在发版时这么做**——这正是用来区分「日常」和「发版」的开关：

| 时机 | dist 怎么处理 |
| --- | --- |
| 平时改 src | 不管它，`.gitignore` 已经挡住了 |
| 本地调试 | 构建就完了，不用提交 |
| **确认稳定、要发版** | `git add -f` 单独加 |

### 需要推哪些文件

```text
dist/性斗学园/性斗学园脚本/index.js        ← 必须。酒馆加载的就是它
dist/性斗学园/性斗学园脚本/index.js.map    ← 不必。3.3MB 调试映射，浏览器才用得上
```

当前该脚本打包为**单文件**（无 `*.chunk.js` 异步分块），所以一条链接就是一个完整版本，
不存在「主文件没变但依赖的分块变了」这种半新半旧的风险。

### 与仓库 CI 的关系（**重要，别做重复功**）

仓库里已有 [.github/workflows/bundle.yaml](../../.github/workflows/bundle.yaml)，它会在每次推送到
`main` 时：删掉 `dist/` → `pnpm install && pnpm build` → 把产物自动提交回仓库（`[bot] bundle`）。

这意味着**理论上你推 `src/` 就够了，机器人会替你构建**。本流程仍写手动 `git add -f`，原因：

- 你想本地先构建、先在酒馆里试过再决定——机器人是"推了就构建"，管不了这一步
- 手动加的产物是你**亲自验过**的那一版，来源明确

> 两者不冲突：本地产物先入库后，机器人会删掉重建，结果应当一致。
> 若发现机器人构建出的产物与你本地验过的不一致，以 **CI 侧为准**（酒馆最终加载的是它）。

## 四、加载进酒馆

角色脚本库里，把性斗学园的脚本条目指向：

```text
https://cdn.jsdelivr.net/gh/vient-awi/my_tavern@main/dist/性斗学园/性斗学园脚本/index.js
```

**不要再从上游链接加载**——那会加载到未性转的原版。

发布后如果酒馆里看到的还是旧版，先去 jsDelivr purge 那个 URL（见第一节）。

## 五、两条自动更新链路的现状（**已停用拉取**）

本分支已把两处会自动拉取上游原版的链路改为**只检测、不拉取**。详见
[自动更新链路风险说明.md](自动更新链路风险说明.md) 第七节。要点：

| 链路 | 现在会做什么 | 不会做什么 |
| --- | --- | --- |
| 脚本更新（[scriptUpdater.ts](性斗学园脚本/scriptUpdater.ts)） | 比对版本、在设置页显示上游最新版、点按钮弹提示 | **不改写脚本 URL、不重载、不拉取上游产物** |
| 世界书（[自动更新世界书脚本/index.ts](自动更新世界书脚本/index.ts)） | 比对版本号、`console.info` + `toastr` 提示 | **不 `importRawCharacter`、不覆盖角色卡** |

**因此「更新酒馆里跑的版本」这件事现在完全由你手动完成**——就是第三、四节的流程。
脚本自身的"检查更新"按钮不再承担发布功能，只负责告诉你上游出到哪一版了。

> 世界书/角色卡的同步流程尚未搭建，属于另一件事，本文档不含。

## 六、常见操作速查

| 我想… | 怎么做 |
| --- | --- |
| 本地试改动的效果 | `pnpm build:dev` → 加载 `dist/…/index.js` |
| 看上游出到哪一版 | `git fetch upstream --tags && git tag -l 'v3.*' \| sort -V \| tail -5` |
| 同步上游改动 | 见 [性转改动对照规则.md](性转改动对照规则.md)（含硬性审核闸门） |
| 发一个稳定版 | 第三节：`pnpm build` → `git add -f …index.js` → commit → push |
| 酒馆里还是旧版 | 去 jsDelivr purge 该 URL |
| 确认改动没搞坏性转 | 跑 [性转改动对照规则.md](性转改动对照规则.md) 第六节的自检清单 |

## 七、边界（本流程**不含**）

- 重新打包角色卡（`pnpm sync`）—— 你选择用脚本外链，不用角色卡
- 世界书/角色卡的同步流程 —— 另行搭建
- 上游代码的合并策略 —— 见 [性转改动对照规则.md](性转改动对照规则.md)
